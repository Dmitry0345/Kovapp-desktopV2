# Kovapp beta 3 — как запустить новую конфигурацию

Kovapp beta 3 — одна версия вместо двух прежних линий: веб-версии (до v22) и
мобильной (до v67). Один сервер обслуживает и сайт, и приложение для Android;
APK собирается из той же папки `web_app`, что раздаёт сервер.

Ниже — запуск на компьютере с Windows (как вы запускали раньше), установка на
рабочий сервер Debian, сборка APK, уведомления, ночные работы и проверка после
установки. Модуль автотестов описан отдельно — `docs/RUNNING.md` в архиве
`kovapp_autotest`.

## 1. Архивы версии

Каждая версия приходит отдельными архивами — по одному на вариант приложения:

| Архив | Что внутри | Куда |
|---|---|---|
| `web.zip` | папка `web`: `server` (сервер, точка запуска `server/server.py`), `web_app` (сайт), `docs`, `sql`, `VERSION`, `vapid_private.pem` (ключ Web Push) | на рабочий сервер (раздел 4) и в модуль автотестов: распаковать в `F:\kovapp_autotest\project` |
| `android.zip` | папка `android`: `mobile` (исходники приложения, сборка APK) и `web_app` (из него собирается интерфейс APK), документы приложения | для сборки APK (раздел 6) и в модуль автотестов: распаковать в `F:\kovapp_autotest\project` |
| `pc.zip` | ПК-версия: программа для Windows, её сборка и установщик (`pc/README.md`) | раздать сотрудникам установщиком; в модуль автотестов: распаковать в `F:\kovapp_autotest\project` |
| `kovapp-server-….zip` | только сервер со всем нужным для запуска на отдельной машине: `server` с полным `requirements.txt`, `web_app`, образец `.env`, служба systemd, инструкция `README-SERVER.md` | на рабочий сервер |
| `kovapp_autotest-….zip` | модуль автотестов | `F:\kovapp_autotest` |

Если в выдаче нет какого-то из архивов, эта часть не менялась.

## 2. Перед обновлением — резервная копия

1. Остановите сервер.
2. Сделайте копию базы (обе базы: основная и мессенджер). На Debian:
   `sudo mysqldump --all-databases --single-transaction > kovapp-before-beta3.sql`.
   На Windows — тем же `mysqldump` из папки MariaDB или через HeidiSQL («Экспорт базы как SQL»).
3. Скопируйте папку с файлами пользователей (`FILE_STORAGE_ROOT` из `.env`) — её содержимое
   новая версия не трогает, но копия не помешает.

При первом запуске сервер сам добавит в базу всё новое (это «миграция», она
идемпотентна — повторный запуск ничего не ломает):

- таблицу телефонов для уведомлений приложения `native_push_devices`;
- у проектов — признак «завершён», кто и когда завершил;
- у реестра файлов `file_blobs` — образец файла для быстрой проверки копии и отметку ночного пережатия;
- индексы для быстрого списка чатов.

## 3. Запуск на Windows (один процесс)

На Windows сервер работает одним процессом — режим `KOVAPP_ROLE=all`, он включён
по умолчанию. Режим нескольких процессов нужен рабочему серверу на Linux (раздел 4).

1. **Python 3.12** и библиотеки (в папке проекта):
   ```
   python -m venv .venv
   .venv\Scripts\activate
   pip install -r server\requirements-v2.txt
   pip install orjson httptools
   ```
   `orjson` ускоряет сборку ответов, `httptools` — разбор запросов. Библиотека `uvloop`
   из инструкции для Linux на Windows не ставится и не нужна.
2. **ffmpeg** должен быть доступен (как раньше): им сервер пережимает видео, которое не
   сжало устройство, и делает обложки.
3. **Файл `.env`** — возьмите прежний. Проверьте строки:

   | Строка | Что указать |
   |---|---|
   | `WEB_APP_DIR` | папка `web_app` **из этой версии** (иначе раздаётся старый сайт) |
   | `FILE_STORAGE_ROOT` | папка с файлами пользователей (как раньше) |
   | `VAPID_SUBJECT` | настоящий адрес: `mailto:ваша@почта` или `https://адрес-сайта`. С заглушкой `example.com` Apple (iPhone, Mac) может отклонять уведомления — сервер напишет об этом в журнал |
   | `KOVAPP_ROLE` | не указывать или `all` |

   Ключ VAPID лежит в `vapid_private.pem` в корне проекта — сервер берёт его сам.
   Если ключа там нет, сервер создаст новый, и браузерам придётся заново разрешить уведомления.
4. **Запуск:** `python server\server.py`. В журнале при старте:
   - «Web Push: включён»;
   - «Уведомления приложения Kovapp: включены, через Google (FCM): да/нет»;
   - «Хранилище файлов: … на месте N».
5. **Сайт:** `http://localhost:54545/app/` (порт — `SERVER_PORT`). В браузере один раз
   нажмите Ctrl+F5, чтобы взять новые файлы сайта.

## 4. Рабочий сервер Debian (2 ядра, 1,9 ГБ)

### 4.1. Код и библиотеки

```
sudo systemctl stop kovapp
# папки server и web_app из архива — поверх старых; .env не перезаписывается
cd /opt/kovcheg && .venv/bin/pip install -r server/requirements-v2.txt
.venv/bin/pip install orjson uvloop httptools
```

### 4.2. Несколько процессов за nginx

Так сервер использует оба ядра: отдельно работают процесс API (запись, фоновые задачи),
процесс переписки (WebSocket), процессы чтения (списки, файлы) и процессы приёма загрузок.
Сколько каких процессов — сервер считает сам по ядрам и памяти.

1. В `.env` сервера:
   ```
   KOVAPP_ROLE=split
   APP_GZIP=0
   ```
   `APP_GZIP=0` — ответы сжимает nginx, а не Python.
2. Блок nginx для Kovapp замените на `docs/nginx-kovapp-example.conf`. В нём четыре адреса:

   | Порт | Процесс | Что туда идёт |
   |---|---|---|
   | 54545 | API | запись, `/health`, ход загрузки |
   | 54546 | переписка | всё, что начинается с `/ws/`: чат сайта и **канал уведомлений приложения `/ws/native-push`** |
   | 54547 | чтение | обычные GET: списки, файлы, страницы |
   | 54548 | приём загрузок | `/upload`, `/uploads/…`, файлы в чат и проекты |

   Проверка и перезагрузка: `sudo nginx -t && sudo systemctl reload nginx`.
3. **Уведомления приложения в режиме нескольких процессов.** Телефоны без Google держат
   канал `/ws/native-push` — он попадает в процесс переписки. Уведомления рождаются в
   процессе API и процессах приёма загрузок; в beta 3 они передаются процессу переписки
   по внутреннему каналу (`127.0.0.1:RT_BUS_PORT`, 8790), поэтому доходят и до Huawei/Honor.
   Телефоны с Google получают уведомления через Google из любого процесса.

### 4.3. MariaDB

Сначала резервная копия (раздел 2). Затем:

```
sudo cp docs/mariadb/60-kovapp.cnf /etc/mysql/mariadb.conf.d/
sudo cp docs/mariadb/kovapp-db-autotune.sh /usr/local/sbin/ && sudo chmod +x /usr/local/sbin/kovapp-db-autotune.sh
sudo mkdir -p /etc/systemd/system/mariadb.service.d && sudo cp docs/mariadb/kovapp-autotune.conf /etc/systemd/system/mariadb.service.d/
sudo systemctl daemon-reload && sudo systemctl restart mariadb
```

Скрипт перед каждым запуском базы считает её настройки по ядрам и памяти машины
(файл `/etc/mysql/mariadb.conf.d/61-kovapp-auto.cnf`). Подробно — `docs/performance-2026-09-28.md`.

### 4.4. Служба systemd

В описании службы Kovapp должно быть:

```
[Service]
WorkingDirectory=/opt/kovcheg
ExecStart=/opt/kovcheg/.venv/bin/python /opt/kovcheg/server/server.py
Restart=always
[Install]
WantedBy=multi-user.target
```

`Restart=always` — служба поднимется сама после сбоя или перезагрузки машины. Упавший
отдельный процесс (например, процесс чтения) сервер перезапускает сам и пишет об этом в журнал
(«Child process … died»). Процесс, который не отвечает на проверку живости, тоже перезапускается —
но только после `WORKER_HEALTHCHECK_S` секунд (по умолчанию 30): при коротком всплеске нагрузки
процессы больше не убиваются, и загрузки в них не обрываются.

Запуск: `sudo systemctl daemon-reload && sudo systemctl start kovapp`. Первая строка журнала
(`journalctl -u kovapp -n 50`): «Kovapp: API на …, переписка на …, чтение на … (процессов N),
приём загрузок на … (процессов M)».

### 4.5. HTTPS

HTTPS нужен для трёх вещей: сжатия видео в браузере (WebCodecs работает только на
защищённых страницах), уведомлений на iPhone и Mac и рабочей сборки APK (она принимает
только `https://`).

```
sudo apt install certbot python3-certbot-nginx
sudo certbot --nginx -d ваш-домен
```

Certbot сам получит сертификат и будет его продлевать.

## 5. Уведомления

| Где | Как работает | Что нужно |
|---|---|---|
| Сайт на компьютере (Chrome, Edge, Firefox) | Web Push | ключи VAPID (уже есть), HTTPS |
| Mac, Safari 16+ | Web Push | HTTPS, настоящий `VAPID_SUBJECT`; разрешить уведомления на сайте |
| iPhone, iOS 16.4+ | Web Push только у сайта, добавленного на экран «Домой» | HTTPS; «Поделиться → На экран „Домой“», открыть Kovapp с экрана «Домой» и включить уведомления в настройках Kovapp |
| Android, приложение с Google | Google (FCM), текст зашифрован ключом телефона | файл ключа Firebase на сервере: `FCM_SERVICE_ACCOUNT_FILE=путь\к\google_key.json` в `.env` |
| Android без Google (Huawei, Honor) | собственный канал приложения | ничего: включается сам, если Google на телефоне или на сервере нет |

Приоритет — Google: телефон выбирает его, если на сервере настроен ключ Firebase, в APK
есть настройки Firebase, на телефоне есть сервисы Google и получен токен. Иначе — собственный
канал. Сервер сам переводит телефон на собственный канал, если Google у него не настроен.

На Safari (iPhone, Mac) уведомление показывается всегда, даже когда сайт открыт: иначе Safari
считает push «тихим» и после нескольких таких отключает подписку. Если сайт открыт, системное
уведомление сразу убирается — человек видит только всплывашку сайта.

Проверка: в Kovapp «Настройки → Уведомления → Проверить уведомление».

## 6. Приложение для Android

Сборка описана в `mobile/README.md`. Коротко:

1. `mobile\kovapp.properties.example` → `mobile\kovapp.properties`, в `serverOrigin` —
   `https://ваш-домен`.
2. Для доставки через Google — значения из файла Firebase `google-services` (`fcmProjectId`,
   `fcmAppId`, `fcmApiKey`, `fcmSenderId`).
3. `mobile\build.bat` — отладочная сборка; рабочая — с подписью (`keystore.properties`).

Сайт и приложение — один код `web_app`: после правки сайта APK нужно пересобрать, чтобы
изменения попали в приложение. Проверить приложение на ПК без телефона —
`mobile\simulator.bat`; на своём смартфоне по USB — `run.cmd demo phone` в модуле автотестов.

## 7. Ночные работы

| Время | Что | Настройки |
|---|---|---|
| 01:00–03:00 | сжатие крупных таблиц с историей (MariaDB, `PAGE_COMPRESSED`); небольшие таблицы сжимаются сразу после запуска | `DB_COMPRESS_HOURS=1-3` (конец не входит) |
| 03:00 | резервная копия базы; удаление старых уведомлений | `BACKUP_HOUR` |
| 03:00–07:00 | ночное пережатие видео | `VIDEO_NIGHT_HOUR=3`, `VIDEO_NIGHT_END_HOUR=7` |

Ночное пережатие:
- ждёт, пока закончатся резервная копия и сжатие таблиц;
- первыми берёт видео, принятые без сжатия на устройстве (например, если сжатие на
  телефоне заняло бы больше 10 минут);
- длинные видео (дольше `VIDEO_LONG_S`, 60 с) уменьшает до HD 1280, остальные — если поток
  выше нормы;
- перед полным сжатием видео длиннее 30 с делает пробу: 10 секунд из середины пережимаются теми
  же настройками (`VIDEO_NIGHT_SAMPLE_S`). Выигрыш пробы явно меньше порога (меньше 10 % при пороге
  15 %, запас — `VIDEO_NIGHT_SAMPLE_MARGIN`) — полное сжатие не тратит процессор, видео отмечается
  проверенным. Иначе выигрыш пробы записывается в базу **до** полного сжатия: такое видео остаётся
  в очереди, пока не будет сжато целиком, — даже если ночь закончилась сразу после пробы, сжатие
  оборвалось или сервер перезапустили. Следующей ночью оно идёт первым, без повторной пробы и
  независимо от давности. Проба не удалась — полное сжатие, как раньше;
- сбой полного сжатия — повтор следующей ночью; после `VIDEO_NIGHT_MAX_ATTEMPTS` (3) сбоев подряд
  видео больше не берётся, в журнале — предупреждение;
- заменяет файл, только если он стал меньше хотя бы на 15 % (`VIDEO_NIGHT_MIN_GAIN`) и
  длительность совпала; иначе оставляет прежний;
- одновременно перекодирует не больше, чем рассчитано для машины (общий предел обработки);
- не успело за ночь — продолжит следующей ночью (смотрит видео за `VIDEO_NIGHT_LOOKBACK_DAYS`, 7 дней).

## 8. Правило размера видео (одно для всех мест)

| Где сжимается | До 60 с | Дольше 60 с |
|---|---|---|
| Браузер (сайт) | Full HD 1920 | HD 1280 |
| Телефон (приложение) | Full HD 1920 | HD 1280 |
| Сервер днём | Full HD 1920 | HD 1280 |

Видео с несколькими звуковыми дорожками везде сжимается с первой дорожкой. Если серверу
не хватает процессора, `VIDEO_SERVER_MAX_SIDE=1280` в `.env` включает режим экономии: всё,
что пережимает сервер, — не больше 1280 (результат будет отличаться от сжатого на устройстве;
тест качества сжатия это покажет).

## 9. Проверка после установки

1. Вход под разными ролями; списки задач и проектов открываются.
2. Отправка фото и видео в задачу и в чат: прогресс, миниатюры, просмотр.
3. Мессенджер: сообщения приходят сразу второму участнику.
4. «Настройки → Уведомления → Проверить уведомление» — на компьютере, iPhone (с экрана
   «Домой»), Android-приложении.
5. Служебные адреса (под директором или администратором):
   `/health/load` — пределы и нагрузка; `/health/db-compression` — сжатие таблиц;
   `/health/file-access` — проверка доступа к файлам.
6. Видео в журнале: по каждому принятому видео сервер пишет строку «Видео: …» — сжато ли оно на
   устройстве (а если нет — почему), что пришло (стороны, кодек, длительность, поток, размер),
   что сохранено и как (без перекодирования или пережато сервером). Посмотреть:
   `journalctl -u kovapp | grep "Видео:"`.
7. Резервная копия базы: после первой ночи (или кнопкой в разделе администрирования) в журнале
   `journalctl -u kovapp | grep kovcheg.backup` должна быть строка об успешной копии. В версии 2
   исправлен сбой «zstd: Allocation error: not enough memory»: копия не создавалась, потому что
   программа сжатия не помещалась в отведённый ей потолок памяти. Если ошибка повторится —
   `BACKUP_COMPRESSOR_MEM_MB=500` в `.env`.
8. Полная автоматическая проверка — модуль `kovapp_autotest`: `run.cmd all`.

## 10. Откат

- Режим нескольких процессов: убрать `KOVAPP_ROLE=split` и `APP_GZIP=0` из `.env`,
  перезапустить службу.
- Версия целиком: вернуть прежние папки `server` и `web_app`. Новые столбцы и таблицы базы
  прежней версии не мешают. При полном откате базы — восстановить копию из раздела 2.
