# Доступ к файлам хранилища

## Принцип

Право открыть файл — это право на ту запись в базе, которой файл принадлежит.
Новых прав и таблиц нет: используются те же проверки, что уже работают для
задач, проектов и чатов.

Раньше маршруты, которые отдают файл по пути (`/file_storage/…`,
`/chat/download/<путь>`, `/file_preview/…`, `/sheet_preview/…`), проверяли
только то, что человек вошёл в систему. Любой сотрудник, узнавший путь, мог
открыть чужое вложение чата или файл чужой задачи. Теперь сервер сначала
находит владельца файла и только потом решает, отдавать ли его.

## Как находится владелец

Путь внутри хранилища однозначно связан с записью в базе. По первой части
пути сразу понятно, где искать:

| Начало пути | Владелец | Где ищется |
|---|---|---|
| `messenger/chat_<номер>/…` | чат | номер чата в имени папки, плюс все сообщения с этим файлом (`messages.file_path`) — так учитываются пересланные сообщения |
| `messenger/avatars/chat_<номер>/…` | чат | номер чата в имени папки и `chats.image_path` |
| `projects/<номер>/…` | проект | номер проекта в пути, запасной путь — `project_files.filepath` |
| `equipment/…` | оборудование | `equipment_items.photo_path` |
| всё остальное | задача | `task_files.filepath` и `task_stage_files.filepath` |

Миниатюры (`….thumb.jpg`) и PDF-превью документов (`….preview.pdf`)
проверяются по исходному файлу: у кого есть право на фото, у того есть право и
на его миниатюру.

## Кто может открыть файл

| Владелец | Право |
|---|---|
| задача | директор и администратор; автор задачи, исполнители, ответственные; участники и ответственные любого её этапа |
| проект | те, кому открыт сам проект (`PROJECT_ACCESS_MODE`: в режиме `open` — все сотрудники) |
| чат | участники чата — любого из чатов, где лежит сообщение с этим файлом |
| оборудование | все сотрудники: раздел открыт всем |
| не найден | никто — это файл-сирота |

## Включение: `FILE_ACCESS_STRICT`

Настройка в `.env`:

- `FILE_ACCESS_STRICT=0` — проверка считается, но не запрещает. Вместо отказа
  в журнал сервера пишется строка «Доступ к файлу: отказ бы был — …» с номером
  сотрудника, путём, владельцем и маршрутом.
- `FILE_ACCESS_STRICT=1` — посторонний получает ответ 403.

Порядок включения:

1. Оставить `0` на неделю и смотреть журнал:
   ```bash
   grep "отказ бы был" logs/app.log*
   ```
2. Если туда попадают обычные действия сотрудников — прислать эти строки на
   разбор, правило дорабатывается.
3. Прогнать поиск файлов-сирот (ниже) и решить, что с ними делать.
4. Пустой журнал — поставить `1` и перезапустить сервер.

## Почему это не тормозит

- По колонкам путей построены индексы (создаются сами при старте сервера,
  шаг миграции `ix_*_filepath`), поиск владельца — точечный запрос.
- Найденный владелец задачи, проекта и оборудования запоминается навсегда:
  пути содержат UUID и не переиспользуются.
- Владелец файла чата запоминается на 60 секунд: файл могут переслать в
  другой чат, и у получателей должен появиться доступ.
- Решение «сотрудник → владелец → можно» запоминается на
  `FILE_ACCESS_CACHE_SECONDS` секунд (по умолчанию 60). Это важно для видео:
  проигрыватель шлёт десятки запросов с Range, и все, кроме первого,
  обслуживаются из памяти.

## Диагностика

С самого сервера (или с токеном директора/администратора):

```bash
curl http://127.0.0.1:54545/health/file-access
```

Ответ показывает режим, размеры кэшей, счётчики проверок и последние 50
случаев «отказ бы был».

## Файлы-сироты

Файл-сирота — файл в хранилище, записи о котором в базе уже нет. После
включения строгого режима он станет недоступен. Поиск запускается из корня
проекта (там, где лежит `.env`):

```bash
python server/find_orphan_files.py                          # только отчёт
python server/find_orphan_files.py --csv orphans.csv        # отчёт в CSV
python server/find_orphan_files.py --move /opt/kovcheg-orphans --yes   # перенести в сторону
python server/find_orphan_files.py --delete --yes           # удалить
```

Временные файлы прерванных загрузок показываются отдельно; ключ
`--with-temporary` добавляет их к переносу или удалению. Перед удалением
разумнее сначала перенести файлы в сторону и неделю подождать.

## Ссылки на файлы в браузере

Адрес картинки или видео нельзя снабдить заголовком авторизации, поэтому
токен уходит в строку адреса. Туда кладётся не токен сессии, а отдельный
файловый токен на 20 минут, который годится только для чтения файлов.
Клиент обновляет его заранее, при возвращении на вкладку и после сна
компьютера, а при ошибке загрузки картинки один раз повторяет запрос со
свежим токеном.
