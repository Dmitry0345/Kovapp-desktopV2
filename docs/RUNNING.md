# kovapp_autotest — полная документация модуля тестирования Kovapp beta 3

Модуль проверяет Kovapp целиком: сервер, веб-версию в браузерах, приложение для Android
(интерфейс APK на ПК и настоящее приложение на эмуляторе или смартфоне), программу для Windows
(ПК-версию), качество сжатия файлов и работу под нагрузкой. Он объединяет два прежних модуля — веб-модуль
`kovcheg-autotest` и мобильный `kovapp_mobile`. Все прежние команды работают.

Команды — для Windows (PowerShell, папка `F:\kovapp_autotest`). На Linux и macOS те же команды
запускаются через `./run.sh`, кроме отмеченных «только Windows».

## 1. Состав

| Часть | Где | Что проверяет | Что нужно |
|---|---|---|---|
| Модуль автотестов | `F:\kovapp_autotest` | сайт, интерфейс APK на ПК, приложение на Android, сжатие, нагрузку, резервные копии — против настоящего сервера с базой | Docker Desktop; для Android — Android Studio |
| ПК-версия (`run.cmd pc`) | `F:\kovapp_autotest\kovtest_pc` | программу для Windows: сжатие и отправку файлов, все разделы под каждой ролью, действия (тема на ходу, переходы, этапы, шаблоны, загрузки), мессенджер — со своим тестовым сервером внутри прогона | Python 3.10–3.12 (64 бита); Docker не нужен |
| Собственные проверки проекта | папка проекта: `mobile\tools`, `mobile\tests\ui`, `server\tests` | код приложения, надстройку APK, сервер по частям, интерфейс на тестовом сервере проекта | Python 3, Java (JDK), Node.js, Playwright |

Модуль поднимает в Docker базу MariaDB и сервер Kovapp из папки веб-версии, заводит учётные
записи всех ролей и тестовые данные, гоняет тесты и убирает за собой.

## 2. Подготовка (один раз)

### 2.1. Docker Desktop

Установите Docker Desktop с включённым WSL 2 (`docs\WINDOWS.md`). Если на компьютере 16 ГБ
памяти и больше, дайте Docker 8 ГБ: файл `%UserProfile%\.wslconfig` со строками
`[wsl2]` и `memory=8GB`, затем `wsl --shutdown` и запуск Docker Desktop.

### 2.2. Папки вариантов приложения

Проект приходит отдельными архивами — по одному на вариант приложения. В каждом архиве уже
есть своя папка, поэтому **все архивы распаковываются в одно место — `F:\kovapp_autotest\project`**:

| Архив | Что в нём | После распаковки | Настройка `.env` |
|---|---|---|---|
| `web.zip` | веб-версия: `server`, `web_app`, `docs`, `sql`, ключ VAPID | `project\web\server\server.py`, `project\web\web_app\…` | `PROJECT_WEB_DIR` |
| `android.zip` | Android: `mobile` (исходники приложения) и `web_app` (из него собирается APK) | `project\android\mobile\app\build.gradle`, `project\android\web_app\…` | `PROJECT_ANDROID_DIR` |
| `pc.zip` | ПК-версия: программа для Windows (`main.py`, `kov`, `ffmpeg` с FFmpeg для сжатия видео) | `project\pc\main.py`, `project\pc\kov\…` | `PROJECT_PC_DIR` |

Перед распаковкой новой версии удалите старое содержимое соответствующей папки. Если архив
распаковали «с лишней папкой» (`project\web\web\server`), модуль сам найдёт вложенную папку.
Если папка пустая, `run.cmd` в начале напишет «ВНИМАНИЕ: … нет веб-версии» или «… нет Android-версии».

Сервер для всех прогонов (и для проверок приложения) берётся из `project\web`. Приложение
собирается из `project\android`. ПК-версия запускается из `project\pc` со своим тестовым
сервером. Если обновилась только одна часть, достаточно заменить её папку.

Ключи Firebase (уведомления Android через Google) — в `F:\kovapp_autotest\keys`: `google_key` —
ключ сервера, `google-services` — файл приложения.

### 2.3. Файл `.env`

В архиве уже есть `.env` со значениями по умолчанию (копия `.env.example`). Пароли в нём —
только для тестовой базы внутри Docker. Главные настройки — раздел 9, все — `docs\SETTINGS.md`.

### 2.4. Android (режимы `android`, `android-device`, `device-*`, `demo android`, `demo phone`)

1. Android Studio; папка SDK — в `.env`: `ANDROID_SDK=F:\Android\Sdk`.
2. Эмулятор: Device Manager → + → Pixel 8, образ с Google Play. Запускать его не нужно —
   `run.cmd` запускает и закрывает его сам.
3. Для телефонов без Google (Huawei, Honor) — второй эмулятор без Google Play, его имя — в `DEVICE_AVD_NOGMS`.
4. Свой смартфон по USB (`demo phone`): «О телефоне» → 7 раз «Номер сборки» → «Для разработчиков» →
   «Отладка по USB»; кабель с передачей данных; на телефоне «Всегда разрешать с этого компьютера».

Подробно — `docs\DEVICE.md`.

### 2.5. Проверить, что всё на месте

`.\run.cmd version` — версии модуля и проектов в папках веб-версии, Android и ПК-версии.

### 2.6. ПК-версия (режим `pc`)

Python 3.10, 3.11 или 3.12 (64 бита) с python.org, в установщике — «Add python.exe to PATH».
Остальное `run.cmd pc` делает сам: создаёт папку `.venv-pc` и ставит в неё библиотеки
ПК-версии (один раз, нужен интернет). Подробно — `docs\PC.md`.

## 5. Слои и экраны

- `LAYERS` (сайт): `api` — запросы к серверу, `ui` — интерфейс, `visual` — вёрстка,
  `realtime` — два пользователя. `LAYERS=api` — только сервер, в разы быстрее.
- `APK_LAYERS` (интерфейс APK): `ui,visual,realtime,mobile`; `DEVICE_LAYERS`: `device`.
- `BROWSERS=chrome,firefox,webkit` (WebKit — движок Safari), `THEMES=light,dark`, `DEVICES=desktop,mobile`.
- `PARALLEL` — число исполнителей (до 8); у каждого свои учётные записи и данные.

## 6. Качество сжатия — `run.cmd compression`

**Зачем.** Фото, видео и документы сжимаются там, где быстрее: в браузере, на телефоне или на
сервере. Результат должен быть примерно одинаковым, где бы ни сжали.

**Исходники** — одни и те же для всех мест (создаются один раз в `logs\compression-inputs`):
фото 4032×3024 (JPEG с «шумом камеры»), PNG 1600×1200, видео 12 с и 64 с в 1080p с потоком
выше нормы (их обязательно сжимать), документ CSV около 1,5 МБ.

**Где сжимается:**

| Место | Как |
|---|---|
| браузеры из `CMP_BROWSERS` | кодом самого сайта в странице: `Kov.ImagePrep`, `Kov.VideoPrep`, `Kov.Gzip`. Если браузер отдаёт видео серверу (например, нет WebCodecs), это записывается в отчёт |
| сервер (`CMP_SERVER=1`) | исходник отправляется «как есть», сервер сжимает сам |
| телефон (`CMP_PHONE`) | в приложении на эмуляторе: видео кладётся в галерею телефона и выбирается так же, как человек, — его сжимает родной кодек (MediaCodec); фото и документы — кодом страницы во встроенном браузере приложения. Если галерея недоступна, видео сжимает встроенный браузер, и в отчёте это видно |
| ПК-версия (`CMP_PC`) | на этом компьютере, без Docker: код программы (`kov.media`) — фото в WebP, видео FFmpeg из её комплекта (OpenH264), документы — gzip. Окна не открываются. Разбор результата и общий отчёт делает второй, короткий прогон в Docker — поэтому в журналах два прогона: `compression` и `compression-pc`, полный отчёт — во втором |

**Сравнение — результаты разных мест между собой, а не с оригиналом.** Насколько видео
уменьшилось (в 2 раза или в 5), не важно. Пример: браузер дал 20 МБ, телефон — 23 МБ,
сервер — 19 МБ: разница между местами 21 %, в допуске. Предупреждение будет, если, например,
телефон дал 45 МБ при 20 МБ у браузера — значит, одно место сжимает заметно иначе.

| Что | Требование | Нарушение |
|---|---|---|
| стороны (фото и видео), частота кадров, звуковые дорожки | точно совпадают | ошибка |
| длительность видео | расхождение не больше `CMP_VIDEO_DURATION_S` (0,1 с) | ошибка |
| документ после распаковки | байт в байт исходный | ошибка |
| сходство с оригиналом (SSIM, 1 — без потерь) | разница между местами не больше `CMP_PHOTO_SSIM_DIFF` / `CMP_VIDEO_SSIM_DIFF` | предупреждение |
| размер файла | разница между местами не больше `CMP_PHOTO_SIZE_DIFF` / `CMP_VIDEO_SIZE_DIFF` / `CMP_DOC_SIZE_DIFF`, % | предупреждение |

**Где результат:** `compression-report.html` в папке прогона — таблица «исходник × место
сжатия» с размером, сторонами, частотой, длительностью, SSIM и решением каждого места.
Результаты каждого места хранятся в `logs\compression-results`: прогон телефона сравнивается
с последним прогоном браузеров, сервера и ПК, и наоборот.

**ПК-версия и размер видео.** Её кодировщик — OpenH264 (без частей под GPL): в нём нет B-кадров и
адаптивного квантования, поэтому на одинаковом качестве файл крупнее, чем у сервера и браузеров.
На настоящих роликах — в среднем на треть, на синтетическом исходнике проверки с сильным шумом —
до двух раз; это предупреждение о размере, а не ошибка. Стороны, частота кадров, длительность и
звук должны совпадать точно.

## 7. Нагрузка по ступеням — `run.cmd load`

Сервер и база урезаются до размеров рабочей машины (по умолчанию сервер — 2 ядра и 1,4 ГБ,
база — полядра и 512 МБ), сервер работает несколькими процессами за nginx, как на рабочем.

**Ступени:** от `LOAD_USERS` (50) до `LOAD_USERS_MIN` (2): 50 → 40 → 30 → 20 → 10 → 5 → 2
(`LOAD_STEPS` — свой список). На каждой: `LOAD_WARMUP_S` (30 с) разгона и `LOAD_STEP_S` (180 с)
замера; между ступенями — пауза, пока очередь загрузок не опустеет и процессор не отдохнёт
(не дольше `LOAD_COOLDOWN_S`). Прогон — около 30 минут.

**Что делают люди на каждой ступени** (одинаково — меняется только их число): переписываются в
группах по 5 (сообщение раз в 1–2,5 с), открывают списки и карточки раз в 2–4 с, отправляют
`LOAD_FILES_PER_USER` файлов в случайные моменты замера (фото и видео, сжатые на телефоне,
документы; `LOAD_RAW_PERCENT` — без сжатия). `LOAD_PHONE_PERCENT` людей — «с телефоном»: у них
ещё канал уведомлений приложения `/ws/native-push`. Живой браузер Chromium
(`LOAD_BROWSER_PROBE=1`) по кругу открывает страницы задач, проектов, мессенджера, уведомлений
и задачи.

**Что меряется на каждой ступени** (медиана и 95 %):

| Показатель | Что это |
|---|---|
| подключение к переписке | открытие WebSocket |
| сообщение в чате | от отправки до получения каждым участником по WebSocket; сколько не дошло |
| уведомление «телефону» | от отправки сообщения до прихода уведомления по каналу приложения |
| списки и карточки | задачи, задача, проекты, уведомления, чаты, история чата — запросом к серверу; отдельно — сколько из этого обработка на сервере; доля ответов «не изменилось» (304) |
| страницы в браузере | время до готовой страницы глазами человека |
| файлы | от начала отправки до ответа сервера: фото, видео, документ, несжатые |
| сервер | процессор в среднем и пик, свободная память, задержка обработки запросов, очередь загрузок, запросов к базе в секунду |

**Проверки:** на каждой ступени — ничего не потерялось и нет ошибок сервера; пороги из `.env`
(`LOAD_*_P95_*`) — на самой большой ступени, как в час пик.

**Где результат:** `load-report.html` — таблица «показатель × ступень» и графики «число людей →
время» (сообщения и уведомления, списки, страницы, файлы, процессор); `load-steps.json` — все
числа; отчёт перезаписывается после каждой ступени. В `full.log` — строка по каждой ступени,
в `db-slow-queries.txt` — медленные запросы базы.

Перед ступенями проверяется, что сервер посчитал свои пределы по урезанной машине. Вместе с
нагрузкой на урезанном сервере идут разделы из `LOAD_SECTIONS` (по умолчанию `files, device,
messenger, realtime`); `LOAD_LAYERS=api` — без браузеров разделов, чтобы они не отнимали память.

## 10. Собственные проверки проекта (без Docker, сервера и телефона)

Из папки проекта (например, `project\web`). Нужны Python 3, JDK (`javac`), Node.js, Playwright с Chromium.

```
python mobile/tools/run_all_checks.py          # пара минут: JVM-тесты, сборка APK, ресурсы, надстройка, безопасность, сервер, JS
python mobile/tools/run_all_checks.py --ui     # то же + тесты интерфейса (около часа)
python mobile/tests/ui/run_ui_tests.py latest  # наборы: parity, rights, overlay, fixes, sim, live, latest
python -m server.tests.native_push_tests       # уведомления приложения: Google, свой канал, несколько процессов
```

Набор `parity` сравнивает снимки сайта и APK (224 снимка), `latest` — последние изменения
(просмотр фото и видео, выбор сообщений, этапы, меню, фильтры на ПК и телефоне, тёмная тема).

## 12. Если что-то не так

| Признак | Что делать |
|---|---|
| «Создан файл .env из .env.example» | проверьте настройки и запустите снова |
| «Docker не найден», «Docker не запущен», «Не работает docker compose» | запустите Docker Desktop; если не помогает — Quit Docker Desktop и запуск снова |
| «Сервер в Docker не запустился» | нет проекта в `project\web` (или в `PROJECT_WEB_DIR`), либо занят порт `FULL_PUBLISH_PORT` |
| «В папке Android-версии нет mobile/app/build.gradle» | распакуйте проект в `project\android` |
| «В папке … ещё один модуль тестов» | архив распакован во вложенную папку — перенесите файлы на уровень выше |
| «Не найден Android SDK», «Нет эмулятора» | `ANDROID_SDK` в `.env`; эмулятор — Device Manager → + |
| «Appium не может подключиться к эмулятору» | разрешите доступ PowerShell и adb в брандмауэре; журнал — `logs\appium-last.log` |
| «FCM: сбой отправки» | контейнеру не ответил DNS — поменяйте `DOCKER_DNS_1`, `DOCKER_DNS_2` |
| `Connection refused` посреди прогона | Docker не хватило памяти: дайте больше, уменьшите `PARALLEL`, нагрузку — с `LOAD_LAYERS=api` |
| прогон прервали | `.\run.cmd stop` |
| `run.cmd pc`: «Не найден Python», «Библиотеки не установились» | Python 3.10–3.12 (64 бита) с python.org с «Add python.exe to PATH»; при смене Python удалите папку `.venv-pc` |

Больше случаев — `docs\DEVICE.md`, `docs\MOBILE.md`, `docs\WINDOWS.md`. Как менять и дописывать
тесты — `docs\CHANGING-TESTS.md`; как передать модуль — `docs\TRANSFER.md`.
